# Elevate Souls Productions Content Creation Command Center
## Universal Original Capability, Effects & Systems Library

**Powered by Aura AI**  
**Company:** Elevate Souls Productions LCN LLC & LTD  
**Tagline:** Elevate Your Soul Through Purposeful Media

This document is the master cross-studio feature-expansion contract for the Command Center. It converts competitor/product research into **original ESP/Aura capability families**. It is not a plan to copy third-party software. Proprietary source code, protected assets, private APIs, trademarks and closed model weights must not be copied or represented as ESP technology.

The machine-readable source of truth is `aura_music_studio/universal_capabilities.py`.

## 1. Product rule

For every useful capability observed in music, voice, video, image, game, LIVE, automation, chatbot, creator-management, overlay, security or media-production software:

1. identify the user outcome and workflow;
2. specify an original ESP/Aura implementation contract;
3. reuse existing Command Center primitives before adding new ones;
4. use provider-neutral adapters where a model/service is optional;
5. support self-host/open models when licensing and infrastructure permit;
6. keep generated and uploaded assets project-centred, versioned and provenance-aware;
7. require explicit consent/rights for voice, face, identity and copyrighted source media;
8. fail closed when a real provider, payment, native client or platform permission is required but not configured;
9. never present a planned feature, mock output or browser-only control as a verified production capability;
10. keep all high-impact automation human-governed and auditable.

## 2. Universal architecture

Every creative surface should consume shared platform services rather than building isolated copies:

- **Project Core:** project metadata, assets, versions, collaborators, comments, approvals, export history.
- **Universal Asset Library:** audio, video, image, 3D, code, fonts, templates, LUTs, SFX, samples, rigs, animations and documents.
- **Capability Registry:** stable IDs, categories, implementation status, surfaces, dependencies and policy.
- **Model/Provider Registry:** local and cloud providers behind common contracts; health, model/version, cost, quota, licence and provenance are first-class.
- **Generation Queue:** priority, cancellation, retries, idempotency, budget, quota and exact project ownership.
- **Effect Graph:** schema-defined non-destructive effects for audio/video/image/LIVE with safe parameter validation.
- **Template Registry:** brand kits, project templates, transitions, captions, titles, lower-thirds, stream scenes, game templates and export profiles.
- **Rights & Consent Ledger:** source ownership, licences, voice/identity consent, model provenance, commercial-use policy and takedown state.
- **Aura Orchestration:** typed tools, project context, approvals, result cards, memory and explainable actions.
- **Audit & Release Evidence:** exact actor, action, asset version, provider/model version, cost and external production evidence.

## 3. Music & recording studio library

Build and maintain original equivalents for: text/lyrics-to-song generation; upload-and-build-around; Song DNA; variable tempo maps; editable chord/key/section analysis; browser multitrack DAW; direct recording; punch/comp/take management; real sampled/self-hosted instrument paths; ensemble builder; drum/groove generator; melody/bass/counter-melody generation; chord/scale assistant; elastic audio; audio-to-MIDI; stem separation; vocal isolation; Aura Tune; manual pitch editing; vocal alignment; doubles/harmonies/choirs; consent-approved singing voice conversion; sample/loop semantic search; DSP pedals and processors; plugin racks; AI effect-chain design; AutoMix; reference mixing; single-track mastering; album mastering; loudness/translation reports; adaptive game/video scores; remote review; timestamp notes; version comparison and release export.

### Music effects catalogue

The common audio-effect schema should cover at minimum:

- EQ: high/low pass, parametric, shelves, tilt, dynamic EQ, resonance removal.
- Dynamics: compressor, multiband compressor, limiter, gate, expander, transient shaper, de-esser, upward compression.
- Spatial: reverb families, convolution, delay, echo, slap, stereo width, Haas/doubler, chorus.
- Modulation: flanger, phaser, tremolo, vibrato, rotary, autopan.
- Saturation: tape, tube, console, soft clip, distortion, overdrive, fuzz, bit crush.
- Pitch/time: pitch shift, formant, harmonizer, octave, time stretch, warp.
- Utility: gain, pan, mono/stereo, polarity, phase alignment, DC removal, loudness normalization.
- Creative: telephone/radio, lo-fi, vinyl, reverse, stutter, glitch, granular, spectral, riser/downlifter, sidechain pump.
- Vocal: tune, de-ess, breath, presence, body, air, warmth, doubling, harmony, choir and vocal-transform chains.
- Mastering: tonal characters, loudness targets, stereo control, reference match, streaming/broadcast profiles.

Presets are data, not hard-coded UI. Every preset must declare compatible input type, safe parameter bounds, tier, preview metadata and renderer support.

## 16. Provider/model adapter contract

Third-party or self-hosted AI engines are interchangeable execution providers, not the product identity. Each adapter must declare:

- provider/model ID and version;
- supported tasks;
- input/output schemas and limits;
- authentication/secrets requirements;
- health/readiness;
- estimated/actual cost;
- latency class and queue behaviour;
- content/licensing restrictions;
- provenance fields;
- cancellation and retry semantics;
- fallback compatibility;
- retention/privacy behaviour;
- whether output is editable into native project primitives.

The UI should say when a capability is unavailable because no compatible provider is configured rather than fabricate an output.

## 18. Completion states

Every capability uses one of these truthful states:

- `existing_foundation`: a real implementation or meaningful tested foundation is already in the repository.
- `planned_original`: accepted scope; original implementation still required.
- `external_release_gate`: repository work cannot complete the requirement without real native/provider/platform/production evidence.
- `research_only`: useful concept retained for evaluation but not accepted build scope.

A capability may move state only with code/evidence. A document edit alone cannot mark it complete.

## 19. Build-chat operating procedure

Every build chat should:

1. read this document and `aura_music_studio/universal_capabilities.py`;
2. inspect the current `development/full-site-build` SHA before changing code;
3. choose a bounded capability slice that avoids conflicts with other active chats;
4. reuse current primitives instead of parallel duplicate systems;
5. implement original code + tests + docs;
6. run or obtain exact-head CI/security/self-host evidence;
7. merge only into `development/full-site-build` after green gates and current-base reconciliation;
8. never merge the integration PR to `main` until production admission gates are independently satisfied;
9. update this library/registry when a capability changes state or gains a new shared dependency.

## 20. Definition of 100%

**Repository code-complete** means every accepted in-repository capability has an implemented and tested code path or is explicitly excluded behind an external boundary.

**Launch-ready** additionally requires real production evidence: domain/TLS; production secrets; monitoring/alerting; backup/restore drill; deployment/rollback; capacity/failure testing; privacy/security review; incident/support readiness; provider/payment E2E; production data/AI infrastructure; and GitHub release-control enforcement.

The platform must never use a percentage to bypass a fail-closed release requirement.
